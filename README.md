# iCE && tEA File Service

Небольшой, но полноценный сервис передачи файлов по сети, реализованный на C++ и Linux.

Проект использует собственный прикладной протокол поверх TCP, поддерживает IPv4 и IPv6, аутентификацию узлов по ключам, шифрование передаваемых данных и обработку большого количества соединений в одном потоке с использованием epoll.

## Аннотация

iCE && tEA File Service представляет собой клиент-серверное приложение для безопасной передачи файлов между заранее известными узлами сети.

Основой транспортного уровня является TCP, что обеспечивает надежную доставку данных. Поверх TCP реализован собственный протокол обмена сообщениями, включающий рукопожатие, взаимную аутентификацию, генерацию общего секрета и передачу файлов с контролем целостности.

Приложение предназначено для работы на Linux и поставляется в виде единого исполняемого файла, который может запускаться как в режиме сервера, так и в режиме клиента.


## Ключевые особенности

### Надежная передача данных

Передача файлов выполняется поверх TCP. Если соединение не разорвано, данные будут доставлены без потерь и в правильном порядке.

### Безопасность

Каждый узел обладает собственной парой ключей.

Перед началом передачи выполняется взаимная криптографическая проверка сторон и формирование общего секрета сессии. После этого весь прикладной трафик шифруется.

### Генерация ключей

Приложение умеет самостоятельно генерировать пары криптографических ключей, используемых для аутентификации узлов и установления защищенных соединений.

Это позволяет быстро подготовить конфигурацию без использования внешних инструментов.

### Без модели "первого доверия"

В отличие от SSH с моделью Trust On First Use, публичные ключи известных узлов заранее задаются в конфигурации.

Это позволяет обнаруживать попытки подмены узла уже при первом подключении.

### Работа по именам серверов

Пользователю не требуется помнить IP-адреса удаленных узлов.

Передача (прием) выполняется по имени сервера, указанному в конфигурационном файле.

Например:

```
filesvc --send office-server report.pdf
```

### Поддержка IPv4 и IPv6

Поддерживаются оба семейства адресов.

### Работа за NAT

Клиент может находиться за NAT (домашний маршрутизатор, корпоративная сеть и т.д.).

Публичный IP-адрес требуется только серверу.

### Проверка свободного места

Перед приемом файла сервис (как в режиме сервера, так и в режиме клиента) проверяет наличие свободного места на диске и может отклонить запрос еще до начала передачи.

### Безопасное сохранение файлов

Получаемый файл никогда не записывается напрямую под конечным именем.

Сначала данные сохраняются во временный файл. Только после успешного завершения передачи он переименовывается в итоговый файл.

Это позволяет избежать повреждения или перезаписи существующих данных при обрыве соединения, ошибках передачи или нехватке свободного места.

### Передача больших файлов

Файл не загружается целиком в память.

Передача выполняется последовательно блоками фиксированного размера, что позволяет работать с файлами любого объема.

Для сетевых буферов используется собственный контейнер на основе std::vector без автоматической инициализации памяти. Это позволяет избежать лишних операций обнуления и копирования при работе с большими объемами данных.

Данные читаются с диска непосредственно в сетевой буфер, затем шифруются и сразу передаются в сеть. Благодаря этому минимизируется количество промежуточных операций с памятью и снижается нагрузка на процессор.

### Эффективное использование сети

Передача выполняется не по одному блоку с ожиданием подтверждения каждого из них. Канал поддерживает окно передачи, внутри которого одновременно могут находиться несколько неподтвержденных блоков данных.

По мере получения подтверждений окно сдвигается вперед и освобождает место для новых блоков. 

Такой подход позволяет эффективнее использовать пропускную способность сети и уменьшает влияние задержек на скорость передачи.

### Подробная диагностика ошибок

Большинство компонентов возвращают подробное текстовое описание последней ошибки, что упрощает поиск проблем и отладку.

### Гибкость сервера

Сервер может запускаться как обычное приложение или работать в фоновом режиме под управлением systemd.

Это позволяет использовать его как полноценную системную службу с автоматическим запуском после перезагрузки, централизованным управлением и встроенными средствами мониторинга Linux.


## Архитектура

Проект построен по принципу разделения ответственности.

Обязанности разделяются между уровнями управления соединениями, реализации прикладного протокола и операций передачи данных.

Каждый уровень отвечает только за свою задачу, что упрощает поддержку проекта и позволяет развивать отдельные части системы независимо друг от друга.

### Менеджеры

Отвечают за:
- создание TCP-соединений;
- работу с epoll;
- обработку системных событий;
- создание и удаление каналов передачи.

### Каналы

Инкапсулируют логику прикладного протокола.

Именно канал определяет, какие сообщения должны быть отправлены, что нужно ожидать от удаленной стороны и как должна развиваться сессия.

### Классы-исполнители

Выделены в отдельные компоненты:
- рукопожатие (Handshake);
- согласование задачи (Task);
- отправка файла (FileSend);
- прием файла (FileReceive).

Такой подход позволяет развивать протокол без превращения одного класса в "божественный объект".

### Контекст сессии

Общие данные активной сессии вынесены в отдельный объект SessionCtx.

Контекст содержит текущее состояние передачи, параметры файла, общий секрет шифрования, сетевые буферы и вспомогательную информацию.

Все компоненты, участвующие в обработке соединения, работают через единый контекст, что позволяет избежать дублирования данных и уменьшить связанность между классами.

### Конечный автомат

Каждый канал передачи представляет собой конечный автомат, который последовательно переводит соединение между состояниями протокола: рукопожатие, согласование задачи, передача данных и завершение работы.

Переход в следующее состояние происходит только после успешного завершения предыдущего этапа либо получения необходимых данных от удаленной стороны.

Преимущества такого подхода:

- логика протокола явно описана;
- отсутствуют скрытые переходы между этапами;
- удобно поддерживать и расширять протокол;
- легко интегрируется с неблокирующей моделью работы.

### Почему epoll

Приложение построено по модели Event-Driven Architecture (Reactor Pattern).

Для обработки сетевых событий используется epoll.

Это дает несколько преимуществ:
- один поток способен обслуживать множество клиентов;
- отсутствуют накладные расходы на переключение контекста потоков;
- минимальное потребление ресурсов в режиме ожидания;
- хорошая масштабируемость при большом количестве соединений.

Несмотря на отсутствие нескольких рабочих потоков, сервер способен одновременно обслуживать множество клиентов.

Такой подход можно рассматривать как эмулированную многопоточность, реализованную через неблокирующую обработку событий.


## Протокол обмена

Передача файла состоит из нескольких этапов.

### Рукопожатие

Клиент:
- сообщает свой публичный ключ;
- отправляет эфемерный ключ сессии;
- подписывает сообщение.

Сервер:
- проверяет клиента по конфигурации;
- проверяет подпись;
- сообщает собственный эфемерный ключ;
- подписывает ответ.

### Генерация секрета

После рукопожатия обе стороны независимо вычисляют одинаковый общий секрет. Секрет никогда не передается по сети.

### Согласование задачи

Клиент отправляет запрос:
- передать файл;
- получить файл.

Сервер:
- проверяет параметры;
- проверяет наличие файла;
- проверяет доступное дисковое пространство;
- принимает или отклоняет запрос.

### Передача данных

После согласования начинается передача блоков файла.

Каждый блок:
- шифруется;
- сопровождается тегом аутентификации;
- подтверждается получателем.

### Контроль целостности

Для каждого сообщения выполняется криптографическая проверка целостности.

Если данные были повреждены либо изменены в процессе передачи, сообщение будет отклонено.

Для защиты от повторного использования сообщений и обеспечения корректной работы шифрования каждая сторона поддерживает два независимых счетчика nonce: входящий и исходящий.

Значения nonce не передаются по сети и не увеличивают размер пакетов. Они вычисляются локально в одинаковом порядке на обеих сторонах соединения. Такой подход возможен благодаря использованию TCP, который гарантирует сохранение порядка доставки данных.


## Конфигурация

Конфигурация хранится в файле `filesvc.conf`.

Файл должен находиться рядом с бинарным файлом или, при использовании systemd, в директории, указанной в параметре `WorkingDirectory` файла `filesvc.service`.

#### Файл содержит:
- настройки локального узла;
- настройки других известных узлов;
- публичные ключи удаленных узлов;
- параметры сетевых подключений.

#### Особенности
- запрещены дубликаты секций;
- запрещено повторное определение параметров;
- неизвестные строки считаются ошибкой;
- обязательна настройка локального узла;
- должен существовать хотя бы один удаленный узел;
- удаленный узел, в зависимости от количества указанных параметров, может быть настроен либо только как клиент (можно только принимать запросы от него), либо как полноценный сервер (можно отправлять запросы ему).

#### Для настройки локального узла обязательно:
- создать секцию `[~]`;
- указать в ней свой приватный ключ ED25519;
- указать существующую директорию (в нее будут сохраняться файлы, запрашиваемые с серверов, и из нее будут отправляться файлы, запрошенные подключающимися клиентами, если локальный узел выступает в роли сервера).

Чтобы локальный узел мог выступать в роли сервера, необходимо также указать свои IP-адрес и порт, на которых сервер будет принимать подключения.

#### Для настройки удаленного узла обязательно:
- создать секцию с именем удаленного узла, например `[office_server]`;
- указать в ней публичный ключ ED25519 удаленного узла.

Чтобы удаленный узел мог выступать в роли сервера, необходимо также указать его IP-адрес и порт, на которых он будет принимать подключения.

#### Параметры конфигурации

- `[~]` - собственная (локальная) секция (к ней относятся все пары ключ-значение, расположенные ниже до следующей секции);
- `[remote_node_name]` - секция удаленного узла (к ней относятся все пары ключ-значение, расположенные ниже до следующей секции);
- `private_key: key` - приватный ключ (относится к локальной секции). Значение - строка без кавычек в формате Base64;
- `public_key: key` - публичный ключ (относится к секции удаленного узла). Значение - строка без кавычек в формате Base64;
- `dir: directory` - рабочая директория (относится к локальной секции). В нее будут сохраняться файлы, полученные от удаленных серверов. Из нее будут передаваться файлы, запрошенные удаленными узлами. Значение - существующая директория;
- `ip: IPv4 или IPv6 адрес` - необходимо указывать, если узел настраивается с возможностью работы в режиме сервера;
- `port: port` - необходимо указывать, если узел настраивается с возможностью работы в режиме сервера.

Пример файла конфигурации приведен в директории `release`.

### Архитектура подсистемы конфигурации

Подсистема конфигурации состоит из нескольких независимых уровней.

Сначала файл разбирается парсером в набор сырых записей. Затем валидатор выполняет проверку структуры конфигурации, параметров и взаимных зависимостей между секциями. После этого результат становится доступен через единый интерфейс доступа.

Такое разделение позволяет независимо развивать этапы разбора и проверки конфигурации.

Например, при необходимости конфигурационный файл можно перевести на формат JSON или любой другой формат без изменения логики валидации. Для этого достаточно реализовать новый парсер, формирующий тот же набор промежуточных данных.

### Проверка конфигурации

До использования приложения можно проверить конфигурацию:

```
filesvc --health
```

Будет выведен результат: готово приложение к работе или нет, а также подробный перечень ошибок.


## Сборка

### Требования

- Linux
- GCC
- CMake
- OpenSSL Development Package

Для Debian/Ubuntu:

```
sudo apt install build-essential cmake libssl-dev
```

Проект использует статическую линковку OpenSSL. После сборки наличие OpenSSL в системе назначения не требуется.

### Инструкции

Обычная сборка CMake:

```
git clone <repository> 
cd <repository> 

mkdir build 
cd build 

cmake -DCMAKE_BUILD_TYPE=Release .. 
cmake --build .
```

Готовый исполняемый файл:

```
release/filesvc
```

Образец конфигурации:

```
release/filesvc.conf
```

Образец .service файла для systemd:

```
release/filesvc.service
```


## Использование

Приложение представляет собой единый исполняемый файл, который может работать как в режиме сервера, так и в режиме клиента. Перед началом работы необходимо сгенерировать ключи, настроить файл конфигурации и убедиться, что конфигурация успешно проходит проверку.

### Основные команды

- Генерирация пары криптографических ключей ED25519, необходимых для аутентификации узла и установки защищенных соединений:

    ```
    filesvc --keygen
    ```

- Проверка корректности конфигурации и вывод подробной информации обо всех обнаруженных ошибках:

    ```
    filesvc --health
    ```

- Запуск приложения в режиме сервера и ожидание входящих подключений от известных (указанных в конфигурации) клиентов:

    ```
    filesvc --listen
    ```

- Отправка файла на удаленный сервер. В качестве `server_name` указывается имя удаленного узла из конфигурационного файла, а `file_path` может содержать как абсолютный, так и относительный путь к файлу на локальной машине:

    ```
    filesvc --send <server_name> <file_path>
    ```

    Пример:

    ```
    filesvc --send office-server report.pdf
    ```

- Запрос файла с удаленного сервера. В качестве `file_name` указывается имя файла, расположенного в рабочей директории сервера:

    ```
    filesvc --recv office-server report.pdf
    ```

    Пример:

    ```
    filesvc --recv office-server report.pdf
    ```

- Для получения полной справки по всем поддерживаемым командам и параметрам достаточно запустить `filesvc` без аргументов. Приложение выведет встроенную справочную информацию.


## Запуск сервера как системной службы (systemd)

Для запуска сервера в фоновом режиме (рекомендуется):

- Убедитесь, что systemd работает на вашем Linux-сервере.

- Отредактируйте файл `filesvc.service` (находится в директории `release`) в соответствии с вашими настройками.

- Скопируйте его в директорию systemd: 

    ```
    sudo cp filesvc.service /etc/systemd/system/
    ```

- Перезагрузите конфигурацию systemd: 

    ```
    sudo systemctl daemon-reload
    ```

- Запустите сервер: 

    ```
    sudo systemctl start filesvc.service
    ```

- Проверьте статус сервера: 

    ```
    sudo systemctl status filesvc.service
    ```

- Добавьте сервер в автозагрузку (чтобы он запускался при старте системы): 

    ```
    sudo systemctl enable filesvc.service
    ```

Управление сервером (через systemd):

- Остановка сервера: 

    ```
    sudo systemctl stop filesvc.service
    ```

- Отключение автозагрузки: 

    ```
    sudo systemctl disable filesvc.service
    ```

## Ограничение

Как клиенту, так и серверу задается строго определенная директория для работы. Запросить файл можно только из нее. Передаваемый файл тоже будет записываться в такую директорию. Такое ограничение вызвано целью создания данного проекта. При этом возможность клиента передать на сервер абслютно любой файл из своей ОС, к которому у него есть права доступа, сохраняется.
